# AI Novelty & Feasibility Audit

Self-critique generated by an AI tool (Claude), as required by the assignment. Written as a genuine critique, not a rubber stamp — weaknesses are named on purpose so they can be addressed before the proposal is finalized.

Strengths
The gap is verified against the closest real prior work, not assumed. DQAF (2026) is genuinely close, but it scores real operator sessions holistically and cannot isolate individual causes — a documented limitation of observational data, not something this project is guessing at. A search for a controlled, per-factor simulation ablation specifically turned up nothing matching this design.
Ground-truth labels come for free. Because the corruption factors are injected in simulation, every demonstration has an exact, known severity for each factor — a real methodological advantage over DQAF, which has to infer quality from behavior alone.
DART gives a credible, directly citable methodological ancestor — controlled noise injection into demonstrations is an established, respected technique in imitation learning; this project is a structured extension of it, not an unprecedented method.
Natural role division across the team. The four sub-tracks the team already sketched (Research, System, Algorithm, Deployment) map cleanly onto four different pieces of one coherent project, which is a good sign for splitting work across teammates.
Red flags — read before finalizing
The experimental grid grows fast, and this is the single biggest risk. Six corruption factors × multiple severities × enough demonstrations per condition to train a behavior-cloning policy × multiple training seeds per condition (needed because BC policy quality is famously noisy run-to-run) multiplies out to a lot of simulation-generation and training runs. Fix: the README already scopes the core deliverable to 3 factors × 2 severities; treat the full 6-factor grid as a stretch goal, and budget at least 2–3 training seeds per condition so the final ranking reflects signal, not training noise.
Isaac Sim has real setup overhead. It's GPU-accelerated, has a nontrivial API, and humanoid asset/rigging setup is its own project by itself if underestimated. Fix: treat "generate one clean demonstration end-to-end in Isaac Sim" as an explicit week-1/2 milestone, and have a named fallback simulator (e.g., MuJoCo, or a simpler manipulator instead of a full humanoid) ready to switch to if Isaac Sim setup stalls past that point — don't discover the fallback decision under deadline pressure in week 6.
"Operator mistakes" isn't like the other five factors and needs its own definition before it can be "controlled." Latency, camera noise, occlusion, reduced resolution, and depth error are all sensor-pipeline corruptions that can be injected deterministically in software. "Operator mistakes" requires either scripting deliberate errors into a teleoperation control policy or having a human operator instructed to err on purpose — neither is as cleanly "graded severity" as turning up a noise parameter. Fix: write an explicit operational definition for what a "mild" vs. "severe" operator mistake means before this factor enters the experimental grid, or drop it to the stretch-goal tier alongside the less-central sensor factors.
Track selection needs an explicit decision, not an implicit one. The team's own framing spans all four official CMPE 249 tracks at once. This audit recommends Research as the primary submission track (the causal ablation is the actual paper-worthy contribution), with System/Algorithm/Deployment as supporting components — but that's a judgment call this audit can't make for the team; confirm it against the rubric or with the instructor before the proposal is finalized.
Don't oversell the "real-time" deployment claim. With the deployment target now the laptop rather than a Jetson (per the team's own resource decision), real-time scoring there is a substantially lower bar than edge-constrained real-time work. Fix: frame the laptop-based ROS 2 quality monitor as a proof-of-concept that the learned scorer can run online, not as a systems/real-time engineering contribution — the actual contribution is the ablation study, and the report should not accidentally lead with the easier claim instead of the harder one.
Verdict

Feasible and novel, conditional on grid discipline. The core idea — a controlled, causal, per-factor ablation of teleoperation demonstration quality — is genuinely unaddressed by the closest existing system (DQAF), and simulation is exactly the right tool to make it answerable in a way real-world data collection cannot. The risk is entirely in scope management: an under-scoped version of this (3 factors, 2 severities, one manipulation task, 2–3 seeds per condition) is very achievable in a semester; the full stated version (6 factors, unspecified severities and seeds, plus a full ROS 2 real-time pipeline, plus three scoring methods compared) is not. Recommend locking the core 3-factor grid in writing before starting simulation work, with the remaining factors and the operator-mistake condition explicitly labeled stretch goals.
